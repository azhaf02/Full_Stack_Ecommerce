# Cart and Checkout

## Shipping method selection

The checkout flow loads active shipping methods from the backend:

`GET /api/shipping-methods`

Shipping methods are stored in the `shipping_methods` database table.

The documented options are:

- Standard Delivery
- Express Delivery
- Same Day Delivery

Confirm availability and the current charge from the API response rather than assuming a fixed charge in documentation.

## Shipping validation

A shipping method must be selected before the customer can continue to checkout review. When no shipping method is selected, the frontend should display a clear validation message, such as:

`Please select a shipping method.`

## Server-side pricing

Checkout prices and totals must be calculated or validated by the backend. Do not trust prices, discounts, shipping costs, tax amounts, or totals supplied by the browser.

The checkout review/session flow validates the relevant cart items, stock, address, shipping method, coupon and pricing data. The checkout-session snapshot is generated by the server and is the source for the subsequent handoff.

Tax and discount behavior must follow the active shared pricing configuration and the applicable backend path. Older notes stating that tax and discount are always zero are not authoritative after the shared pricing configuration changes. Do not document a fixed rate unless it has been verified against the active configuration.

## Checkout API flow

### Review

`POST /api/checkout/review`

The request includes the selected address and shipping method. A coupon code is optional. The backend validates the checkout data and returns a review based on server-side information.

### Create checkout session

`POST /api/checkout/session`

Authentication: customer bearer token required.

The session flow revalidates checkout information on the server and returns a checkout reference, session identifier, status, expiry, and validated checkout snapshot. The documented session lifetime is 30 minutes; verify the implementation if this value changes.

### Payment/order handoff

The frontend should retain `checkout_reference_id` and pass it to the Payment/order handoff as required by the current API contract. The receiving module must use that reference to retrieve or validate the pending checkout and must not trust browser-supplied totals.

`POST /api/orders` is also part of the project order API. See the Order creation section below for the source-inspected request contract and the distinction between checkout-reference and direct-items order paths. This documentation does not replace runtime or manual acceptance evidence.

## CHK-06: Checkout-to-order handoff

The checkout-session contract is intended to carry validated checkout information from review to the next stage. The session snapshot contains server-generated checkout data, including items and summary totals.

The frontend should not replace this validated snapshot with client-supplied prices or totals. Any changes to the handoff contract should be coordinated with the responsible module owner.

## CHK-09 API contract reference

The following contracts were checked against the backend source during this documentation review. This is a source review, not proof that the endpoints passed runtime or browser testing.

### Checkout review

`POST /api/checkout/review` requires an authenticated customer. Its request schema accepts:

- `address_id` (integer)
- `shipping_method_id` (integer)
- `coupon_code` (optional string or `null`)

The request schema forbids extra fields. The handler checks that the selected address belongs to the current customer and that the selected shipping method is active; invalid address or shipping-method input returns HTTP 400. The review response includes `items`, `coupon`, `summary` (`subtotal`, `discount`, `tax`, `shipping`, `total`) and `ready_for_payment`.

### Singular checkout handoff session

`POST /api/checkout/session` accepts the same review request, re-runs checkout review, and requires `ready_for_payment` to be true before creating a session. The session stores a server-generated checkout snapshot and uses a 30-minute expiry. The response includes `checkout_reference_id`, `session_id`, `status`, `expires_at` and the validated `checkout` review.

### Plural checkout-session lifecycle API

The separate lifecycle router is mounted at `/api/checkout/sessions`:

- `POST /api/checkout/sessions` creates an authenticated customer's session and returns `session_id`, `customer_id`, `status`, `created_at` and `expires_at`.
- `GET /api/checkout/sessions/{session_id}` retrieves a session for its owner.
- The inspected handler returns 404 for a missing or non-owned session and 410 for an expired/inactive session.

These plural lifecycle endpoints are distinct from `POST /api/checkout/session`, which creates the checkout handoff snapshot. Do not treat the routes as interchangeable.

## Additional verified API details

### Active shipping methods

`GET /api/shipping-methods` returns active shipping methods. The inspected response schema contains:

- `id`: shipping method identifier
- `name`: display name
- `cost`: shipping charge
- `estimated_days`: estimated delivery duration in days
- `status`: active/inactive flag

The inspected handler filters for active methods and orders results by identifier. Confirm current charges from the API response; do not hard-code them.

### Order creation

`POST /api/orders`

Authentication: customer bearer token required. The endpoint returns HTTP `201 Created` with an order detail response.

The request requires `payment_method` (`ONLINE` or `COD`) and exactly one purchase source:

- `checkout_reference_id`: uses the server-side snapshot created by `POST /api/checkout/session`. Optional address or shipping IDs must match the snapshot if supplied.
- `items`: direct order path. Each item contains `product_id`, optional `variant_id`, and `quantity` from 1 to 100. This path also requires `address_id` and `shipping_method_id`.

The request schema rejects extra fields. Client-supplied prices, discounts, shipping charges, taxes and totals must not be trusted.

According to the inspected route, COD orders return with status `CONFIRMED`. Online orders return with status `PLACED` and are confirmed after the payment module reports verified `SUCCESS`. These are source-contract details, not evidence of a successful manual test.
